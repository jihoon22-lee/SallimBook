# SallimBook v1 잔여 작업 실행 계획

기준일 2026-10-18. R-01~R-22, SB-005~040, 최종 추적 Issue [#49](https://github.com/jihoon22-lee/SallimBook/issues/49).
운영 안정화와 Android 자동 검증을 병행하고, 자동화로 대체할 수 없는 기기 검증을 마지막에 모은다.
아래 완료 기준과 실제 실행 근거를 구분한다. 계획 작성만으로 통과 처리하지 않는다.

2026-10-18 진행: [실제 암호화 백업과 격리 복원 무결성 확인](testing/operating-backup-restore.md)을
완료했다. 사용자 요청에 따라 외부 백업·키 보관 위치 결정은 나머지 개발과 운영 시작 뒤로 미룬다.
독립 사본이 없는 동안 보존 도구는 원본을 삭제하지 않는다. 이 유예를 독립 보관 완료로 표시하지 않는다.

## 계획 수립 시 출발점

- 현재 운영 후보는 0.1.2, versionCode 3이다. 구현 소스 `f017d8f61bfeae2304f0109d6f62c9fd13643212`,
  병합 기준 `b3db1e5271e4747fb4996b51c14678bfe3bce9a4`, PR #85/#86/#88에 근거가 있다.
- 7개 필수 영역의 코드·화면과 실제 웹/API·서명 APK가 배포됐다. 사용자에게서 본인 휴대전화의
  앱 로그인 성공을 확인했다. 이 보고를 두 기기의 보안·업데이트·전체 사용 검증으로 확대하지 않는다.
- 현재 계정이 사용 중이다. 최초 등록 가능 여부를 다시 열거나 운영 bootstrap·데이터 초기화·
  합성 계정 생성으로 시험하지 않는다. 개발·클라우드 시험은 별도 합성 가계와 DB를 사용한다.
- 이전 전체 검사와 최근 변경 검사의 실행 범위는 [통합 기록](testing/final-integration.md),
  [등록 통합 기록](testing/mobile-onboarding.md)에 있다. 서로 다른 실행 수를 더해 새 전체 결과로 쓰지 않는다.
- 계획 수립 당시 Android 계측은 `SecureBridgeWebViewTest` 4개와 `NativeVaultCvcAcceptanceTest` 8개가
  준비돼 있다. APK 패키징까지 수행했으며 에뮬레이터 실행 결과는 없다. 7개 영역의 실제 Android
  화면을 통과하는 자동 시나리오와 격리 HTTPS 시험 환경은 추가 구현 대상이다.
- 일반 CVC gate는 false다. R-12는 미충족 상태로 유지하며 검증 없이 v1에서 제외하거나 켜지 않는다.

## 백업과 운영 작업 상세

### 백업 생성과 독립 보관

1. 현재 운영 배포 manifest·DB 역할·암호화 첨부 위치를 읽기 전용으로 확인한다. 비밀번호·키 원문은
   기존 private 파일에서 도구가 읽고 채팅·명령행 값·로그·이슈에 노출하지 않는다.
2. 기존 `ops.backup`으로 일관된 DB/첨부 snapshot의 암호화 백업을 만들고 완료 receipt와 checksum을 검증한다.
   실제 운영 자료를 합성 시험 fixture나 클라우드 Android 시험으로 복사하지 않는다.
3. 사용자에게 속한 별도 저장장치/NAS/클라우드 중 확정된 위치에 암호문을 복제하고 다시 checksum을 대조한다.
   같은 PC의 다른 폴더에 복사한 것은 독립 보관 완료로 세지 않는다.
   현재 위치 결정은 사용자 요청으로 운영 시작 뒤로 유예했으며, 유예 중 원본 자동 삭제는 하지 않는다.
4. APK 서명키, 서버 field keyring, 백업 복호화키를 데이터 백업과 분리해 보관한다. 복원 대상 중 가장 오래된
   백업에 필요한 키를 유지한다. 보관함 복구코드는 사용자 소유로 두며 운영 백업에 원문을 넣지 않는다.
5. 실제 운영 백업의 복원 확인은 운영자가 관리하는 격리 환경에서 수행하고 원문을 보고서/AI 입력에 내보내지
   않는다. schema·행 수·암호화 객체 무결성·복구 절차만 기록한다. 기능·계산 회귀 시험에는 합성 데이터를 쓴다.

### 복원과 주기 작업

- 외부 API/Tailscale에 연결되지 않은 새 빈 복원 DB와 새 첨부 경로를 쓴다. 현재 운영 DB로 복원하지 않는다.
- [운영 절차](operations-runbook.md)에 따라 무결성·키 의존성·기존 인증 폐기와 복원 후 보관함 회전 절차를 대조한다.
  카드 암호문 복원과 사용자의 복호화 성공은 구분하고, 복구키가 없다고 보관함을 초기화하지 않는다.
- RPO 24시간/RTO 4시간은 목표다. 최초 백업·복원 시각을 측정해서 실제 결과를 기록한다.
- 일별 14개·주별 8개·월별 12개를 기본 보존안으로 삼고, 독립 복사/완료 receipt가 검증된 백업만 정리 대상으로
  삼는다. 최근 복원 가능한 사본과 필요한 키를 보호하며 자동 삭제는 먼저 합성 파일의 dry-run으로 검증한다.
- 정기 백업, 실패 상태 기록, 월간 격리 복원 작업을 SallimBook 전용 실행 단위로 구성한다. 중복 실행 잠금,
  누락 감지, 중단/디스크 부족/잘못된 경로/복사 실패를 검증한다. 외부 알림 채널은 따로 확정하기 전 발송하지 않는다.

### 서버 자동 복귀와 첨부 검사

- 기존 WSL 서비스·컨테이너·호스트 Tailscale 설정을 보존한다. 전용 Compose 프로젝트와 전용 시작 작업만 사용한다.
- 서비스 단위 재시작부터 검증한다. Windows/WSL 전체 재시작은 다른 작업에 영향이 있으므로 최종 일정만 조율한다.
  PC 전원이 꺼진 동안 계속 서비스된다고 표현하지 않는다. 상시 별도 호스트 이전은 현재 기본 계획에 포함하지 않는다.
- DB/scanner/API 상태, 디스크 여유, 마지막 완료 백업, 검사 DB 나이를 비밀 없이 기록한다. 상태 불명확을 정상으로
  처리하지 않으며 API 프로세스만 살아 있는 것을 첨부 검사 정상으로 보지 않는다.
- 현재 첨부 검사 DB가 7일을 넘으면 업로드를 거절한다. 만료 전 정기 갱신 이미지 제작·검증·배포를 구성하고,
  갱신 실패 시 상태를 알린다. 신선도 검사나 실패 시 거절을 끄지 않는다.

## CI와 변경 소유 범위

원격 CI `39087600798`과 후속 `39091077393`은 runner/step 시작 전에 실패했다.
후속 실행의 job 재시도도 runner ID 0, steps 없음으로 실패했다. 사용자가 실제 실행 화면의 annotation을
확인해 GitHub 계정의 Actions 결제/예산 제한에 따른 사전 차단임을 전달했다. 이는 코드 테스트 실패와
구분한다. 처음에는 CLI의 Checks 조회도 403이었으며 사용자 화면 확인으로 원인을 확인했다.
이후 사용자의 명시적 요청으로 Git 전체 기록의 비밀 검사를 수행하고 저장소를 공개로 전환했다.
공개 전환 뒤 annotation API 조회와 원격 runner 시작을 직접 확인했다. `d8585dc`의 실행
`39093133775`를 재실행했고, 후속 화면 변경 PR #93의 `39094729822`와 통합 PR #91의
`39095407683`에서 일반 CI 7개 job 성공을 확인했다. 별도 Android 계측 workflow의 실패는
일반 CI 성공에 합쳐 숨기지 않으며, 최종 통합 commit은 다시 그 실행 결과로 판정한다.
비용·결제수단은 변경하지 않았다. [GitHub 공식 진단 안내](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows#reviewing-billing-errors)를 따른다.

현재 환경은 `ops/`, 운영 문서, `.github/workflows/`, 출시 통합을 담당한다. 클라우드는 Android 계측·
시험 harness·시험용 debug 설정·결과 문서를 담당한다. Android 시험에 필요한 Gradle 의존성과 그 잠금 파일은
클라우드 작업이 전담하며, 변경 이유·고정 버전·호환 시험을 함께 제시한다. API 계약·마이그레이션·공통 잠금 파일의
변경이 필요하면 별도 수정 작업으로 분리하고 담당을 먼저 정한다. 서로 같은 파일을 동시에 수정하지 않는다.

각 기능 수정은 작은 PR로 나눠 해당 Issue·요구사항·테스트 결과·보안 영향을 기록한다. 기존 지시대로 자동 리뷰는
PR당 최대 3회까지 사용하고, 남은 지적은 실제 수정/근거로 처리한다. 검증 없이 리뷰 횟수만 채워 병합하지 않는다.
계획 문서 PR은 앱/API/APK payload를 변경하지 않으므로 배포 빌드를 다시 만들지 않는다.

기존 ops 전체 Ruff 진단 6개는 도구 변경 범위에서 정리한다. 웹 bundle 크기 경고는 Android 구동 성능을 측정한 뒤
사용 지연이 확인되면 별도 최적화한다. 단순히 경고 임계값을 올리거나 관련 없는 전면 개편을 하지 않는다.

## 실제 기기에서 마지막으로 확인할 항목

현재 기기 기준은 S24 Ultra와 S25 Ultra다. 실행 시 실제 OS·WebView·빌드·서명 정보를 기록한다.

- 네이티브 입력, 앱 잠금, 인증 취소/잠금 제한/미등록, 화면 잠금과 늦은 응답 경합.
- 실제 강력한 생체 인증에 묶인 Keystore 연산, 인증수단 변경 후 키 무효화와 복구.
- 카드 표시 30초 제한, 화면 이탈·회전·최근 앱·캡처/기록 차단, 평문 bridge/저장소/로그 비노출.
- 합성 CVC의 로컬 저장·실패 복원·백업/기기 이전 제외. debug 검증 통과와 일반 release 활성화는 별개다.
- 두 구성원의 새 기기·보관함 복구·키 회전과 취소/중단 복구, 실제 패스키/RP/DAL 연결.
- 같은 정식 서명키의 업데이트 후 입력 자료 보존, 두 기기와 PC의 교차 조회·409 충돌, TalkBack·확대 글꼴.
- 허용되지 않은 별도 기기의 사설 접근 거부. 정상 기기에서 헤더만 바꾼 시험으로 대체하지 않는다.

CVC 보안 인수가 통과하면 별도 PR에서 일반 Android 경로의 gate 활성화를 검토·반영하고,
이미 구현된 사용자 동의·직접 입력을 정식 후보에서 다시 회귀 검사한다. 검증 없이 현재의 상수 gate를 켜거나
debug 합성 예외를 release로 옮기지 않는다.
기기별 직접 입력·명시적 저장 선택·삭제·기본 미저장 동작을 유지하고, 이 단계까지 끝나야 R-12를 완료 처리한다.

사용자에게는 자동화로 확인하지 못한 기기 조작만 한 번에 모아 전달한다. 지금 다시 ADB 페어링이나 개발자 옵션을
요청하지 않는다. 기존 폰의 생체 등록·잠금수단 제거·앱 삭제처럼 사용자 자료에 영향을 주는 시험은 합성 전용 환경을
우선 사용하고, 개인 기기에 적용할 때 영향과 복구 방법을 구체적으로 확인한다.

## 사용자에게 필요한 입력과 출시 판단

현재 계획을 진행하기 위해 즉시 추가 답변을 받을 필요는 없다. 아래 정보는 해당 단계가 준비됐을 때만 필요하다.

| 필요한 정보 | 그 전까지 진행할 작업 |
|---|---|
| 별도 클라우드 세션의 Android 검증 결과 | 사용자가 이미 작업을 전달했다. 현재 환경은 운영 자동화·UI 개선·통합을 진행하고 결과가 오면 대조 |
| 이 PC와 독립된 백업/키 보관 위치 | 사용자 요청으로 운영 시작 뒤 결정. 로컬 암호화 백업·격리 복원·보존/복제 도구를 준비하며 외부 사본 없이는 원본을 삭제하지 않음 |
| 실제 기기 확인과 호스트 재시작을 할 수 있는 때 | 자동 시험과 수정, 전용 시험 앱·간단한 수행 순서·복구 절차까지 준비 |
| 외부 서비스 계정/비용 또는 권한이 실제로 필요한 경우 | 정확한 필요성과 준비된 실행 항목을 전달. 준비 없이 가입·설정부터 요구하지 않음 |

최종 결과표는 `PASS / FAIL / SKIPPED / BLOCKED_ENV / NOT_RUN`을 구분하고, 각 행에 실행 commit,
환경·기기·명령·증거 위치·제한을 연결한다. 실제 통과한 조건만 이슈에서 닫는다. 모든 기능·운영·보안 조건을
충족하기 전에는 0.x 후보 상태와 남은 항목을 유지한다.
