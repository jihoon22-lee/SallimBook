# 보안·인증 정책

정책 버전 0.1. 구현·검증 전 설계이며 보안 인증 취득을 의미하지 않는다.
기술적 사실의 출처는 [참고 자료](references.md)에 모았다. 숫자로 정한 잠금 시간 등은 이 프로젝트의 설계 정책이다.

SB-005/007에서 비밀번호·초대·웹/native 서버 세션과 가계 권한·멱등성 기반을 구현했다.
Argon2id는 64 MiB·3회·4 lanes로 고정했고 개발 WSL에서 해시 중앙값 60.8ms, 검증 56.2ms를 측정했다.
배포 환경의 자원 제한 아래에서 다시 측정한다. SB-006은 패스키의 서버 검증과 목적별 증명을 추가했다.
PC/Android 패스키 UI, native 자격증명 보관, 앱 잠금·보관함의 구현·실기기 게이트와는 구분한다.

초기 등록 CLI는 비밀번호를 인자로 받거나 토큰을 stdout에 출력하지 않는다. 운영자 소유 0700 디렉터리의
새 0600 파일에 15분 등록 코드를 쓰며 Git 작업 디렉터리와 symlink 경로·기존 파일 덮어쓰기를 거부한다.
구성원이 없는 단일 가계의 만료 코드는 `renew-bootstrap`으로 교체하며 이전 초대를 모두 폐기한다.
활성 구성원 제한은 가계 행 잠금과 slot 1/2 CHECK·partial UNIQUE를 함께 사용한다.
로그인 제한 기록은 15분 창이 만료되면 다음 인증 시도에서 최대 64개씩 정리한다.
만료 시각 인덱스를 사용하고 정리 잠금과 카운터 잠금을 분리하며, 진행 중인 제한은 유지한다.

## 1. 데이터 분류와 신뢰 경계

| 분류 | 예시 | 저장·표시 원칙 |
|---|---|---|
| 일반 관리정보 | 제품명·소모품 모델·카드 별칭 | 인증된 가계 접근 |
| 민감 금융·건강정보 | 잔액·수입·진료명·보험문서·계좌번호 | 서버 권한, 저장/백업 암호화, 공개 링크 금지 |
| 보관함 비밀 | 전체 PAN·유효기간 | 클라이언트 암호화, 일반 API는 last4만 |
| 기기 로컬 비밀 | CVC/CVV | Android 네이티브 로컬만, 전송/백업 금지 |
| 인증·복구 비밀 | 비밀번호·refresh token·복구코드·서명키 | 전용 저장·해시·접근제한, 로그 제외 |

일반 DB와 의료 문서는 서버에서 집계·처리하므로 서버 운영자를 신뢰한다.
**앱 전체가 E2EE라는 설명은 금지한다.** 카드 보관함도 서버가 악성 웹 코드를 배포할 경우 웹의 잠금 해제 시 공격될 수 있다.
보관함 암호화는 저장소/백업 유출에 대한 보호와 노출 최소화이며 감염된 기기를 무력화하는 보증이 아니다.

## 2. 인증의 세 층

### 계정 인증

부부 각각의 계정과 서버 세션을 만든다. 공개 회원가입은 없다.
최초 관리자는 운영 CLI로 일회성 등록 경로를 만들고 두 번째 사용자는 15분 유효 초대를 사용한다.
등록 이후 초대 기능은 제한하고 두 계정을 초과하지 않게 DB 트랜잭션에서 검사한다.
비밀번호는 Argon2id 해시로 저장하고 서버 리소스에 맞춰 비용을 측정한다([S07](references.md)).
패스키는 PC WebAuthn, Android Credential Manager 경로로 구현한다([S05, S06](references.md)).
RP ID·origin·challenge·user verification·한 번 사용 여부를 서버에서 검증한다.
Android 앱과 도메인 연결에 Digital Asset Links 및 실제 앱 서명 정보가 필요하므로 정식 서명 전에 설정을 검증한다.
패스키 등록/새 기기 허용은 기존 계정의 최근 재인증을 요구한다.

SB-006 서버는 `webauthn==3.0.1`의 등록·서명 검증을 사용한다.
32바이트 난수 challenge는 5분 유효·일회성이고 DB에는 해시만 남긴다.
RP ID, 정확한 origin, user presence/verification, credential ID/소유권, 공개키 서명과 카운터를 검증한다.
cross-origin/top-origin assertion은 거부한다. 등록 요청은 현재 계정의 5분 이내 실제 로그인과
동일 세션·기기 범위를 요구한다. 로그인 성공은 비밀번호 로그인과 같은 세션 발급기를 사용한다.
등록 옵션/검증은 세션 → 등록 기기 순서로 행을 잠그고 현재 만료·폐기·최근 로그인 상태를 다시 확인한다.
이 잠금은 credential 생성까지 유지하므로 HTTP 인증 직후 기기 폐기가 완료된 요청은 패스키를 추가할 수 없다.
공개키·카운터·인증기 공개 메타데이터만 저장하며 attestation `none`을 하드웨어 신뢰 증명으로 해석하지 않는다.

운영 RP/domain/certificate를 추정해서 넣지 않는다. `SALLIMBOOK_WEBAUTHN_RP_ID`와 해당 transport의
origin 목록이 비어 있으면 ceremony를 503으로 거부한다. 웹은 RP ID와 동일한 호스트의 정확한 HTTPS origin을
패스키 목록과 일반 허용 origin 목록 양쪽에 설정해야 한다. 하위 도메인·와일드카드·HTTP를 자동 허용하지 않는다.
native origin은 실제 앱 서명 인증서의 SHA-256을 패딩 없는 base64url로 표현한
`android:apk-key-hash:…` allowlist로 제한한다. 개발/운영 서명과 applicationId를 혼용하지 않는다.
Digital Asset Links의 실제 도메인·패키지·서명 인증서 설정과 실기기 검증은 아직 미완료다.

웹은 HttpOnly/Secure/SameSite 쿠키와 CSRF 방어를 사용한다.
Android는 native auth adapter가 refresh token을 Keystore 보호 저장소에 보관하며 일반 JS storage에 저장하지 않는다.
일반 API 호출에 필요한 짧은 access token은 메모리로 제한하고 로그/URL로 보내지 않는다.
설계 기본값은 access token 10분, refresh 세션 30일 상한, 재사용 탐지 시 해당 세션 폐기다.
웹 세션은 유휴 30분·절대 12시간을 초기 정책으로 두고 실제 사용성을 검증한다.
서버는 토큰 소유만 아니라 계정/기기/가계의 활성 상태도 확인한다.

step-up은 별도의 인증된 challenge로 발급하는 2분 일회용 증명이다. 가계·사용자·세션·기기·purpose·target에
바인딩하며 `grant_token` 원문은 로그·URL·영구 저장소에 두지 않는다.
현재 소비 동작은 `household.invite`(가계 UUID)와 `device.revoke`(본인 기기 UUID)다.
동작의 권한·사전 조건·버전 검사를 통과한 뒤 `X-Step-Up-Token`을 검증하고 변경과 같은 트랜잭션에서 소비한다.
명시된 증명이 유효하지 않으면 최근 로그인 상태라도 거부한다. 증명이 없을 때만 기존 최근 로그인 검사를 사용한다.
보호 작업은 세션 → 관련 기기 전체(UUID 정렬) → 가계/도메인 → 패스키 → 증명 순서로 잠근다.
기기 폐기는 원본 기기와 대상 기기를 최초 잠금에 함께 포함하며 일반 읽기 인증은 기기 잠금을 추가하지 않는다.
초대의 최근 비밀번호 로그인 경로도 같은 원본 기기 보호를 적용한다. 패스키·기기 폐기와 증명 소비는
변경 commit까지 서로 직렬화하고, 잠금 대기 후 현재 세션/기기의 활성 상태와 증명·최근 로그인 만료를 다시 확인한다.
증명 검색 결과는 후보 ID 발견에만 사용하고 패스키 잠금 뒤 증명 전체 바인딩을 잠금 상태로 다시 조회한다.
step-up 발급도 기기를 먼저 잠가 새 증명의 FK 확인과 기기 폐기 사이에 잠금 역순이 생기지 않게 한다.
step-up은 `authenticated_at`을 갱신하지 않으므로 다른 목적에 재인증을 대신 제공하지 않는다.
등록/패스키 폐기는 현재 최근 로그인으로만 허용한다. enum에 있는 다른 목적은 해당 소비 동작을 구현하기 전까지
권한을 부여하지 않는다. 자세한 요청 순서는 [API 계약](api-contract.md)의 목적별 step-up 절차를 따른다.

만료된 challenge·grant는 새 ceremony 발급 때 `expires_at` 인덱스로 테이블당 최대 100건씩 정리한다.
정리 대상은 만료된 행뿐이며 `FOR UPDATE SKIP LOCKED`로 검증/소비 중인 행을 기다리지 않는다.
정리 자체는 commit하지 않아 현재 세션 잠금과 트랜잭션 경계를 유지한다.
다음 발급이 없으면 만료 행이 즉시 삭제되지는 않지만 만료 시점부터 검증·소비는 거부한다.

### 앱 잠금

Android 앱 시작·백그라운드 복귀 시 잠금 상태를 판정한다. 기본은 백그라운드 1분 이후 앱 잠금.
서버 세션이 없으면 지문 성공만으로 새 로그인을 만들지 않는다.
시스템 BiometricPrompt를 사용하며 생체정보 원문은 받지 않는다([S03](references.md)).
기기 PIN·패턴·비밀번호 허용 여부는 지원 API/키 설정과 일치시켜 실제 기기에서 검증한다.
앱 잠금은 화면 보호이며 서버 인증이나 vault 해제의 대체가 아니다.

### 비밀 열람

카드 전체 정보는 앱 잠금이 풀려 있어도 별도로 재인증한다.
Android는 Keystore 키의 실제 사용과 BiometricPrompt CryptoObject를 결합한다([S03, S04](references.md)).
단순 성공 콜백이나 JS 플래그를 보안 근거로 삼지 않는다.
PC는 별도 보관함 암호로 암호키를 로컬에서 해제한다. 패스키 인증 성공만으로 AES 키가 생긴다고 가정하지 않는다.

## 3. 표시·입력 보호

전체 정보 표시는 최대 **30초**, 화면 이탈·앱 백그라운드·화면 잠금·로그아웃 때 즉시 가린다.
표시한 정보를 재사용 가능한 일반 앱 상태에 두지 않는다. 메모리 정리는 best-effort이며 완전 소거를 보증하지 않는다.
Android 보안 화면은 FLAG_SECURE로 캡처/비보안 디스플레이 노출을 줄인다([S13](references.md)).
외부 카메라·루팅·손상된 OS까지 차단할 수는 없다.

Android 보안 입력은 자동완성/키보드 학습/클립보드/화면분석 노출을 최소화하는 설정을 검증한다.
CVC는 네이티브 전용 입력에서만 받는다. 기본 복사 기능은 제공하지 않는다.
PC 브라우저는 스크린샷 차단을 보장할 수 없으며 표시 전 이에 대한 안내를 제공한다.
앱/웹 분석 SDK, session replay, 네트워크 요청 본문 수집은 도입하지 않는다.

## 4. CVC/CVV 정책과 적용 범위

PCI SSC FAQ 1280은 서비스 제공자 등의 승인 후 보안코드 보관을 암호화 여부와 관계없이 금지한다고 설명한다.
FAQ 1574는 소비자가 자기 기기에 직접 입력하는 경우를 FAQ의 적용 대상과 구분한다([S08, S09](references.md)).
이는 SallimBook의 적합성 인증이나 법적 허가가 아니다. '로컬이면 무조건 허용/안전'이라고 쓰지 않는다.

제품 정책은 다음과 같다.

- 본인/공동 가계 사용자가 자기 Android 기기에 직접 입력한다.
- 가계 서버, DB, 객체 저장소, PC 웹, 브라우저 로컬 저장소, 로그, 내보내기에는 보내지 않는다.
- Android cloud backup, device-to-device transfer, 앱 자체 백업 모두에서 제외한다.
- `allowBackup=false` 하나로 제조사별 기기 이전까지 막혔다고 판단하지 않는다. noBackupFilesDir와 백업/전송 규칙을 함께 검증한다([S12](references.md)).
- 재설치·기기교체 시 다시 입력한다. 서버 복구 기능으로 CVC를 되살리지 않는다.
- 카드 앞뒷면 사진·스크린샷·첨부로 우회 저장하는 기능은 제공하지 않는다.
- 서비스 공개/타인 사용/결제대행으로 범위가 바뀌면 CVC 기능을 비활성화하고 별도 검토한다.

## 5. 권한·API·첨부

모든 ID를 가계 범위 안에서 검증한다. 다른 가계 fixture를 사용한 권한 침해 테스트를 필수로 둔다.
CORS와 숨겨진 URL은 권한 통제가 아니다. 민감 응답은 no-store, cookie 요청은 CSRF 방어를 수행한다.
계좌번호 전체 보기, 데이터 내보내기, 기기 추가/폐기, 보관함 구성원 변경에는 최근 계정 재인증을 요구한다.
문서는 DB에서 권한·연결 상태를 확인한 뒤 전달하며 외부 공개 URL을 영구 저장하지 않는다.
파일 형식/크기/실행 위험을 확인하고 HTML/SVG 같은 실행 가능한 형식은 v1 첨부에서 제외한다.

## 6. 로그와 감사

기록할 수 있는 것: actor ID, 자원 ID, 작업 종류, 시각, request ID, 성공/실패, 버전.
일반 금액 정정 이력은 가계 접근 권한으로 보호한다.
기록하지 않는 것: 전체 PAN·CVC·유효기간 평문·계좌번호 원문·비밀번호·인증토큰·복구코드·진료서류 원문.
보관함 작업 감사에는 '열람 요청/실패' 같은 메타정보만 포함한다. 지문 결과를 서버가 직접 검증했다고 기록하지 않는다.
서버에서 볼 수 없는 로컬 화면 표시 성공은 클라이언트 보고라는 신뢰 수준을 구분한다.

## 7. 복구·분실

계정 복구와 보관함 복구를 분리한다. 계정 비밀번호 재설정으로 카드 암호화를 해제할 수 없어야 한다.
기기 분실 신고는 해당 세션과 등록 상태를 즉시 폐기한다.
이미 기기에 있었던 비밀의 원격 삭제는 오프라인 상태에서 보장할 수 없다.
공유 키를 가진 구성원 철회 시 새 키로 재암호화하고 예전 복사본 회수 불가능성을 고지한다.
상세 절차는 [키 수명주기](vault-key-lifecycle.md)에 따른다.

## 8. 출시 보안 게이트

G1: 정상/타가계 권한, 세션 만료·재사용·CSRF 확인.
G2: 보관함 암호화 벡터, nonce/AAD, 키 분리·회전·복구 확인.
G3: 실기기 지문 변경·잠금·취소·백그라운드·앱 강제종료·재설치 확인.
G4: 프록시·로그·DB·백업·bridge·WebView 상태에서 CVC/PAN 평문 유출 검사.
G5: 웹 XSS/의존 스크립트 경계와 첨부 접근, 네이티브 bridge 입력 검증.
G6: 운영 백업 복원·APK 서명·업데이트·분실 대응 실증.

보안 게이트가 실패한 기능을 숨긴 채 v1 완료로 처리하지 않는다.
