# 보안·인증 정책

정책 버전 0.1. 설계와 현재 구현 경계를 기록하며 보안 인증 취득을 의미하지 않는다.
실행한 검사와 미실행 실기기 게이트는 [통합 검증 기록](testing/final-integration.md)에서 구분한다.
기술적 사실의 출처는 [참고 자료](references.md)에 모았다. 숫자로 정한 잠금 시간 등은 이 프로젝트의 설계 정책이다.

SB-005/007에서 비밀번호·초대·웹/native 서버 세션과 가계 권한·멱등성 기반을 구현했다.
Argon2id는 64 MiB·3회·4 lanes로 고정했고 개발 WSL에서 해시 중앙값 60.8ms, 검증 56.2ms를 측정했다.
배포 환경의 자원 제한 아래에서 다시 측정한다. SB-006은 패스키의 서버 검증과 목적별 증명을 추가했다.
native 자격증명 보관은 아래 경계로 구현하며, PC/Android 패스키 UI·앱 잠금·보관함과 실기기 검증은 별도 게이트 대상이다.

Issue #87부터 기본 첫 사용은 [모바일 직접 시작](adr/mobile-first-start.md)이다. 웹/Android에서
이름·비밀번호를 정하면 계정 생성과 세션 발급을 원자적으로 완료한다. 배포에서 명시한 사설망
사용자 헤더와 실제 전용 프록시 peer를 함께 확인하며, 사용자/구성원 기록이 있으면 다시 열지 않는다.
배우자는 인증된 첫 구성원이 만든 8자리 연결 코드로 등록 즉시 로그인한다. 15분·한 번 사용,
웹/native 공통 설치 단위 5회 시도 제한을 적용한다. 기존 긴 초대와 로그인 경로는 유지한다.

기존 호환·운영용 초기 등록 CLI는 비밀번호를 인자로 받거나 토큰을 stdout에 출력하지 않는다. 운영자 소유 0700 디렉터리의
새 0600 파일에 15분 등록 코드를 쓰며 Git 작업 디렉터리와 symlink 경로·기존 파일 덮어쓰기를 거부한다.
구성원이 없는 단일 가계의 만료 코드는 `renew-bootstrap`으로 교체하며 이전 초대를 모두 폐기한다.
운영의 migration·runtime 역할 준비 후, 전용 DB 환경을 주입한 비공개 운영 도구 container에서
다음 CLI를 실행한다. 출력 디렉터리는 실행 UID 소유 0700으로 별도 mount하고 기존 파일은 재사용하지 않는다.

```bash
python -m sallimbook.identity.cli bootstrap \
  --household-name HOUSEHOLD_NAME --login-name FIRST_LOGIN_NAME \
  --token-file /PRIVATE_ENROLLMENT/NEW_INVITATION.json
# 구성원이 없는 가계의 등록 코드가 만료된 경우에만:
python -m sallimbook.identity.cli renew-bootstrap \
  --login-name FIRST_LOGIN_NAME --token-file /PRIVATE_ENROLLMENT/NEW_REPLACEMENT.json
```

기존 CLI 등록 코드는 기기의 기존 초대 등록 화면에서 사용할 수 있다. 새 기본 시작 흐름은
운영자 코드 전달을 요구하지 않는다. 코드 파일의 원문을
로그·채팅·Issue에 붙여 넣지 않는다. 실제 계정 생성은 합성 검증과 별도 운영 단계다.

활성 구성원 제한은 가계 행 잠금과 slot 1/2 CHECK·partial UNIQUE를 함께 사용한다.
로그인 제한 기록은 15분 창이 만료되면 다음 인증 시도에서 최대 64개씩 정리한다.
만료 시각 인덱스를 사용하고 정리 잠금과 카운터 잠금을 분리하며, 진행 중인 제한은 유지한다.

## 1. 데이터 분류와 신뢰 경계

| 분류 | 예시 | 저장·표시 원칙 |
|---|---|---|
| 일반 관리정보 | 제품명·소모품 모델·카드 별칭 | 인증된 가계 접근 |
| 민감 금융·건강정보 | 잔액·수입·진료명·보험문서·계좌번호 | 서버 권한, 저장/백업 암호화, 공개 링크 금지 |
| 보관함 비밀 | 전체 PAN·유효기간 | 클라이언트 암호화, 일반 API는 last4만 |
| 기기 로컬 비밀 | CVC/CVV | Android 네이티브 로컬만, 전송/백업 금지 |
| 인증·복구 비밀 | 비밀번호·refresh token·복구코드·서명키 | 전용 저장·해시·접근제한, 로그 제외 |

일반 DB와 의료 문서는 서버에서 집계·처리하므로 서버 운영자를 신뢰한다.
**앱 전체가 E2EE라는 설명은 금지한다.** 카드 보관함도 서버가 악성 웹 코드를 배포할 경우 웹의 잠금 해제 시 공격될 수 있다.
보관함 암호화는 저장소/백업 유출에 대한 보호와 노출 최소화이며 감염된 기기를 무력화하는 보증이 아니다.

## 2. 인증의 세 층

### 계정 인증

부부 각각의 계정과 서버 세션을 만든다. 불특정 인터넷 공개 회원가입은 없다.
최초 사용자는 허용된 사설망 연결에서 이름·비밀번호로 직접 시작하고 두 번째 사용자는 15분 유효
연결 코드를 사용한다. 첫 계정 `owner`와 연결 계정 `partner`는 가계 안의 두 사용자이며 외부 회원가입이 아니다.
등록 이후 초대 기능은 제한하고 두 계정을 초과하지 않게 DB 트랜잭션에서 검사한다.
비밀번호는 Argon2id 해시로 저장하고 서버 리소스에 맞춰 비용을 측정한다([S07](references.md)).
패스키는 PC WebAuthn, Android Credential Manager 경로로 구현한다([S05, S06](references.md)).
RP ID·origin·challenge·user verification·한 번 사용 여부를 서버에서 검증한다.
Android 앱과 도메인 연결에 Digital Asset Links 및 실제 앱 서명 정보가 필요하므로 정식 서명 전에 설정을 검증한다.
패스키 등록/새 기기 허용은 기존 계정의 최근 재인증을 요구한다.

SB-006 서버는 `webauthn==3.0.1`의 등록·서명 검증을 사용한다.
32바이트 난수 challenge는 5분 유효·일회성이고 DB에는 해시만 남긴다.
RP ID, 정확한 origin, user presence/verification, credential ID/소유권, 공개키 서명과 카운터를 검증한다.
cross-origin/top-origin assertion은 거부한다. 등록 요청은 현재 계정의 5분 이내 실제 로그인과
동일 세션·기기 범위를 요구한다. 로그인 성공은 비밀번호 로그인과 같은 세션 발급기를 사용한다.
등록 옵션/검증은 세션 → 등록 기기 순서로 행을 잠그고 현재 만료·폐기·최근 로그인 상태를 다시 확인한다.
이 잠금은 credential 생성까지 유지하므로 HTTP 인증 직후 기기 폐기가 완료된 요청은 패스키를 추가할 수 없다.
공개키·카운터·인증기 공개 메타데이터만 저장하며 attestation `none`을 하드웨어 신뢰 증명으로 해석하지 않는다.

운영 RP/domain/certificate를 추정해서 넣지 않는다. `SALLIMBOOK_WEBAUTHN_RP_ID`와 해당 transport의
origin 목록이 비어 있으면 ceremony를 503으로 거부한다. 웹은 RP ID와 동일한 호스트의 정확한 HTTPS origin을
패스키 목록과 일반 허용 origin 목록 양쪽에 설정해야 한다. 하위 도메인·와일드카드·HTTP를 자동 허용하지 않는다.
native origin은 실제 앱 서명 인증서의 SHA-256을 패딩 없는 base64url로 표현한
`android:apk-key-hash:…` allowlist로 제한한다. 개발/운영 서명과 applicationId를 혼용하지 않는다.
Digital Asset Links의 실제 도메인·패키지·서명 인증서 설정과 실기기 검증은 아직 미완료다.

웹은 HttpOnly/Secure/SameSite 쿠키와 CSRF 방어를 사용한다.
Android는 native auth adapter가 refresh token을 Keystore 보호 저장소에 보관하며 일반 JS storage에 저장하지 않는다.
일반 API 호출에 필요한 짧은 access token은 메모리로 제한하고 로그/URL로 보내지 않는다.
설계 기본값은 access token 10분, refresh 세션 30일 상한, 재사용 탐지 시 해당 세션 폐기다.
웹 세션은 유휴 30분·절대 12시간을 초기 정책으로 두고 실제 사용성을 검증한다.
서버는 토큰 소유만 아니라 계정/기기/가계의 활성 상태도 확인한다.
로그인한 계정의 비밀번호 재확인은 전용 `reauthenticate` 경로에서 기존 세션의 최근 인증 시각만 갱신한다.
새 기기·세션·토큰을 만들거나 절대 만료를 연장하지 않는다. 실패한 비밀번호 확인은 기존 세션을 유지하며,
시도 제한 기록을 저장한 뒤 세션·기기를 다시 잠그고 폐기/만료를 확인한다.

현재 Android 계정 인증 구현은 다음 경계를 따른다.

- 비밀번호·초대 코드 입력과 생성 코드 표시는 비공개 네이티브 Activity에서 처리한다. JS에는 완료/취소 상태만 반환한다.
- access token은 네이티브 메모리, refresh token은 앱·API origin에 바인딩한 AAD와 Keystore AES-GCM으로 보호한 `noBackupFilesDir` 파일에 둔다. 계정 세션 키는 보관함의 생체인증 필수 키와 다르다.
- refresh는 계정 executor에서 직렬로 한 번만 전송한다. 저장된 암호문은 요청 본문을 쓰기 직전에 소비한다. 본문을 쓰기 전 실패(화면 이탈·앱 잠금·DNS·연결 실패)는 저장된 토큰을 그대로 둔다. 서버가 401이 아닌 응답(429·5xx 등)을 주면 같은 토큰을 다시 저장한다. 본문을 보낸 뒤 응답이 불명확하면 이전 토큰을 재사용하지 않고 재로그인을 요구한다. 회전 응답은 화면이 비활성이어도 먼저 저장하고 결과만 전달하지 않는다. 서버 401만 계정 세션 종료로 보고 보관함 로컬 등록까지 지운다. 일시적 실패와 응답 불명확은 보관함 로컬 등록을 지우지 않는다.
- OkHttp 전용 클라이언트는 쿠키·리디렉션·자격증명 요청 자동 재전송·인증 자동응답·캐시·HTTP 로그를 사용하지 않는다. 플랫폼 TLS 검증을 유지하며 WebView의 전역 CookieHandler와 분리한다.
- bridge는 번들 `https://localhost`의 주 프레임 메시지만 허용한다. 보안 메시지 리스너 미지원/설치 실패 시 구형 `androidBridge`를 설치하지 않고 앱 진입을 막는다. iframe/object 로드를 CSP로 차단한다.
- 메타데이터 요청은 경로·메서드·쿼리·If-Match를 제한한다. 응답도 각 엔드포인트의 명시적 필드와 타입으로 검증하며 서버 오류의 원문 메시지를 전달하지 않는다.
- 로그아웃은 로컬 자격증명을 지운다. 네트워크 실패로 서버 폐기를 확인하지 못한 경우 이를 별도로 안내한다.
- 로그인·재인증 실패나 취소는 사용할 수 있는 기존 자격증명을 먼저 지우지 않는다. 새 로그인 응답을 검증하고 refresh 암호문 저장이 성공한 뒤 교체한다. 시도 제한(429)은 비밀번호 오류와 구분해 "잠시 후 다시 시도해 주세요."로, 서버 오류(5xx)는 연결 안내로 표시한다.
- cloud backup과 device transfer 제외 규칙을 함께 두지만 제조사 이전·Keystore 보안 수준·실제 화면 캡처 방지는 아직 실기기에서 검증하지 않았다.

step-up은 별도의 인증된 challenge로 발급하는 2분 일회용 증명이다. 가계·사용자·세션·기기·purpose·target에
바인딩하며 `grant_token` 원문은 로그·URL·영구 저장소에 두지 않는다.
현재 소비 동작은 `household.invite`(가계 UUID)와 `device.revoke`(본인 기기 UUID)다.
동작의 권한·사전 조건·버전 검사를 통과한 뒤 `X-Step-Up-Token`을 검증하고 변경과 같은 트랜잭션에서 소비한다.
명시된 증명이 유효하지 않으면 최근 로그인 상태라도 거부한다. 증명이 없을 때만 기존 최근 로그인 검사를 사용한다.
보호 작업은 세션 → 관련 기기 전체(UUID 정렬) → 가계/도메인 → 패스키 → 증명 순서로 잠근다.
기기 폐기는 원본 기기와 대상 기기를 최초 잠금에 함께 포함하며 일반 읽기 인증은 기기 잠금을 추가하지 않는다.
초대의 최근 비밀번호 로그인 경로도 같은 원본 기기 보호를 적용한다. 패스키·기기 폐기와 증명 소비는
변경 commit까지 서로 직렬화하고, 잠금 대기 후 현재 세션/기기의 활성 상태와 증명·최근 로그인 만료를 다시 확인한다.
증명 검색 결과는 후보 ID 발견에만 사용하고 패스키 잠금 뒤 증명 전체 바인딩을 잠금 상태로 다시 조회한다.
step-up 발급도 기기를 먼저 잠가 새 증명의 FK 확인과 기기 폐기 사이에 잠금 역순이 생기지 않게 한다.
step-up은 `authenticated_at`을 갱신하지 않으므로 다른 목적에 재인증을 대신 제공하지 않는다.
등록/패스키 폐기는 현재 최근 로그인으로만 허용한다. enum에 있는 다른 목적은 해당 소비 동작을 구현하기 전까지
권한을 부여하지 않는다. 자세한 요청 순서는 [API 계약](api-contract.md)의 목적별 step-up 절차를 따른다.

만료된 challenge·grant는 새 ceremony 발급 때 `expires_at` 인덱스로 테이블당 최대 100건씩 정리한다.
정리 대상은 만료된 행뿐이며 `FOR UPDATE SKIP LOCKED`로 검증/소비 중인 행을 기다리지 않는다.
정리 자체는 commit하지 않아 현재 세션 잠금과 트랜잭션 경계를 유지한다.
다음 발급이 없으면 만료 행이 즉시 삭제되지는 않지만 만료 시점부터 검증·소비는 거부한다.

### 앱 잠금

Refs #18, #38: 이 구현은 SB-029의 앱 잠금 부분이며 카드 보관함·실기기 보안 게이트 완료를 의미하지 않는다.
프로세스 시작은 잠금 상태다. 같은 프로세스에서 외부 백그라운드가 60,000ms 미만이면 복귀할 수 있고,
1분 이상이면 다시 인증한다. `elapsedRealtime`으로 시간을 판단하며 잠금 해제 상태를 디스크·Bundle에 저장하지 않는다.
화면 꺼짐·기기 잠금 확인·수동 잠금은 즉시 잠근다. 앱 내부의 로그인·계좌번호 화면 전환은 외부 백그라운드와 구분한다.
Activity 일시정지 시 네이티브 가림 화면을 먼저 표시하고 비밀번호 입력을 지운다.

API 30 이상에서 플랫폼 `BiometricPrompt`의 `BIOMETRIC_STRONG | DEVICE_CREDENTIAL`을 **앱 화면 잠금 전용**으로 사용한다.
이 선택은 기기 PIN·패턴·비밀번호를 허용하며 자체 앱 PIN이나 별도 암호키를 만들지 않는다.
성공 콜백은 현재 요청 세대·포그라운드·창 초점·기기 잠금을 다시 확인한 뒤에만 소비한다.
이 로컬 인증은 서버의 최근 로그인 시각·step-up 증명·보관함 키를 변경하지 않는다.
미등록·잠금 제한·기기 인증 실패 시 네이티브 입력으로 현재 계정의 서버 비밀번호 재인증을 수행할 수 있다.
검증된 서버 응답 후에만 같은 세대에서 해제하며 기존 세션·기기를 유지한다. 이 경로의 실제 비밀번호 재인증은 서버 최근 로그인을 갱신한다.
로컬 세션이 없으면 네이티브 로그인·초대 수락만 제공하며 생체 인증 성공으로 새 로그인을 만들지 않는다.

가림 화면은 WebView를 숨기고 뒤쪽 접근성 접근을 막는다. MainActivity도 `FLAG_SECURE`를 사용한다.
잠긴 동안 `getSession`은 refresh나 `/me`를 호출하지 않고 `APP_LOCKED`를 반환한다.
일반 metadata·계좌번호·패스키 보호 동작은 요청 생성 세대와 잠금 상태를 토큰 접근·HTTP 전송·본문 쓰기·응답 전달에서 확인한다.
잠금은 대기·진행 요청을 취소하며 해제 후에도 이전 세대의 응답은 재사용하지 않는다.
로그인·초대·재인증·명시 로그아웃 예외는 각 인증 경로로만 제한하고 금융 API에는 사용할 수 없다.
JS 잠금 이벤트는 화면·입력·캐시 폐기에만 사용한다. JS bool이나 Intent 결과로 해제하는 API는 없다.

플랫폼 API 선택은 [공식 Builder 계약](https://developer.android.com/reference/android/hardware/biometrics/BiometricPrompt.Builder#setAllowedAuthenticators(int))과
[인증 가이드](https://developer.android.com/identity/sign-in/biometric-auth)를 확인했다. 새 라이브러리는 추가하지 않았다.
실제 Galaxy에서 PIN·지문·취소·최근 앱·화면 잠금·프로세스 재시작 검증은 전체 기능 개발 뒤에 수행하며 현재 미실행이다.
카드 보관함의 strong 생체 인증과 실제 `CryptoObject` 키 사용 정책은 별도로 유지한다.

앱 잠금 자동 검증(2026-10-18, WSL 분리 작업 트리):

- `pnpm install --frozen-lockfile`, `pnpm android:sync`, client `typecheck`: 성공, 의존성/lockfile 변경 없음.
- JDK 21/SDK 36의 `:app:testDebugUnitTest :app:assembleDebug :app:compileReleaseKotlin :app:processReleaseMainManifest`: 성공. JVM 73개 중 앱 잠금 정책 14개, 실패·오류·건너뜀 0개.
- `pnpm exec playwright test --config playwright.finance.config.ts --workers=2`: 데스크톱/Android 크기 전체 168개 성공. 새 잠금 시뮬레이션은 초기 차단·입력 폐기·조작된 해제 이벤트 거절·명시 잠금을 확인한다.
- `pnpm test:docs`: 문서 검증 및 도구 테스트 40개 성공. 별도 작성자의 소스 검토에서 발견한 취소 직후 서버 응답 경합은 요청 모니터 안에서 최종 해제를 결정하도록 수정하고 실제 helper 회귀를 추가했다.

JVM/브라우저 시뮬레이션은 실제 OS 인증·FLAG_SECURE·백업 보호를 증명하지 않는다.
두 Galaxy의 미실행 항목은 콜드 시작/강제종료/회전, 59초·60초 복귀, 내부 네이티브 화면 전환,
화면 꺼짐/잠금, 기기 인증 취소·등록 변경·잠금 제한·PIN 전환, 서버 비밀번호 실패/만료/취소,
최근 앱·스크린샷·접근성 뒤쪽 화면, 잠금 중 늦은 HTTP 응답이다. 실기기 증거가 확보되기 전 #18/#38의 출시 보안 게이트를 완료로 표시하지 않는다.

### 비밀 열람

카드 전체 정보는 앱 잠금이 풀려 있어도 별도로 재인증한다.
Android는 Keystore 키의 실제 사용과 BiometricPrompt CryptoObject를 결합한다([S03, S04](references.md)).
단순 성공 콜백이나 JS 플래그를 보안 근거로 삼지 않는다.
PC는 별도 보관함 암호로 암호키를 로컬에서 해제한다. 패스키 인증 성공만으로 AES 키가 생긴다고 가정하지 않는다.

## 3. 표시·입력 보호

전체 정보 표시는 최대 **30초**, 화면 이탈·앱 백그라운드·화면 잠금·로그아웃 때 즉시 가린다.
표시한 정보를 재사용 가능한 일반 앱 상태에 두지 않는다. 메모리 정리는 best-effort이며 완전 소거를 보증하지 않는다.
Android 보안 화면은 FLAG_SECURE로 캡처/비보안 디스플레이 노출을 줄인다([S13](references.md)).
비밀을 표시하는 TextView는 API 34 이상에서 `ACCESSIBILITY_DATA_SENSITIVE_YES`로 표시해 접근성 도구가 아닌 서비스에 숨긴다. TalkBack 같은 접근성 도구는 계속 읽는다.
외부 카메라·루팅·손상된 OS까지 차단할 수는 없다.

Android 보안 입력은 자동완성/키보드 학습/클립보드/화면분석 노출을 최소화하는 설정을 검증한다.
CVC는 네이티브 전용 입력에서만 받는다. 기본 복사 기능은 제공하지 않는다.
PC 브라우저는 스크린샷 차단을 보장할 수 없으며 표시 전 이에 대한 안내를 제공한다.
앱/웹 분석 SDK, session replay, 네트워크 요청 본문 수집은 도입하지 않는다.

## 4. CVC/CVV 정책과 적용 범위

PCI SSC FAQ 1280은 서비스 제공자 등의 승인 후 보안코드 보관을 암호화 여부와 관계없이 금지한다고 설명한다.
FAQ 1574는 소비자가 자기 기기에 직접 입력하는 경우를 FAQ의 적용 대상과 구분한다([S08, S09](references.md)).
이는 SallimBook의 적합성 인증이나 법적 허가가 아니다. '로컬이면 무조건 허용/안전'이라고 쓰지 않는다.

제품 정책은 다음과 같다.

- 본인/공동 가계 사용자가 자기 Android 기기에 직접 입력한다.
- 가계 서버, DB, 객체 저장소, PC 웹, 브라우저 로컬 저장소, 로그, 내보내기에는 보내지 않는다.
- Android cloud backup, device-to-device transfer, 앱 자체 백업 모두에서 제외한다.
- `allowBackup=false` 하나로 제조사별 기기 이전까지 막혔다고 판단하지 않는다. noBackupFilesDir와 백업/전송 규칙을 함께 검증한다([S12](references.md)).
- 재설치·기기교체 시 다시 입력한다. 서버 복구 기능으로 CVC를 되살리지 않는다.
- 카드 앞뒷면 사진·스크린샷·첨부로 우회 저장하는 기능은 제공하지 않는다.
- 서비스 공개/타인 사용/결제대행으로 범위가 바뀌면 CVC 기능을 비활성화하고 별도 검토한다.

## 5. 권한·API·첨부

모든 ID를 가계 범위 안에서 검증한다. 다른 가계 fixture를 사용한 권한 침해 테스트를 필수로 둔다.
CORS와 숨겨진 URL은 권한 통제가 아니다. 민감 응답은 no-store, cookie 요청은 CSRF 방어를 수행한다.
계좌번호 전체 보기, 데이터 내보내기, 기기 추가/폐기, 보관함 구성원 변경에는 최근 계정 재인증을 요구한다.
SB-011 계좌번호는 서버가 복호화하는 필드 암호화이며 카드 보관함의 클라이언트 키와 분리한다.
번호 공개는 세션/원본 기기 → 자산 → 계좌 → 패스키/증명 순서로 잠그고 폐기 작업과 직렬화한다.
최근 비밀번호 로그인과 `account.reveal` 증명 모두 도메인 잠금 대기 뒤 현재 상태를 검증한다.
복호화 전후와 감사 기록 flush 후 세션/기기·최근 로그인 또는 같은 증명의 만료를 재확인하고 commit한다.
실패하면 증명 소비·감사를 함께 롤백하며 계좌번호 원문을 응답하지 않는다.
`SALLIMBOOK_FIELD_ENCRYPTION_KEY_FILE`이 지정하는 서비스 소유의 절대 경로 파일에서 AES-256 키를 읽는다.
파일 권한은 0400/0600이고 경로의 심볼릭 링크를 허용하지 않는다. 키 원문을 환경변수·Git·로그·API 응답에 넣지 않는다.
키 파일은 `schema_version: 1`, 양의 정수 `active_key_version`, 정수 버전 문자열에서 표준 base64 32바이트 키로 연결하는 `keys` 객체를 가진다.
새 저장은 active 버전을 사용하며 기존 번호 복호화에는 해당 버전 키를 보존해야 한다. 계좌번호 변경마다 새 nonce를 생성한다.
키 파일 미설정/손상·해당 버전 누락 시 번호 저장/복호화는 503으로 실패한다. 번호 없는 metadata 처리와 번호 제거는 허용한다.
이 변경에서 운영 키를 생성하지 않았으며, 운영 키 준비·백업·복구 시험은 배포 절차에서 수행한다.
문서는 DB에서 권한·연결 상태를 확인한 뒤 전달하며 외부 공개 URL을 영구 저장하지 않는다.
파일 형식/크기/실행 위험을 확인하고 HTML/SVG 같은 실행 가능한 형식은 v1 첨부에서 제외한다.

SB-023 첨부는 **서버가 복호화하는 일반 데이터**다. 외부 keyring의 키에서 HKDF-SHA256의
문서 전용 purpose로 키를 분리하고 AES-256-GCM의 새 12바이트 nonce를 사용한다.
AAD에는 가계/문서 ID·키 버전·MIME·크기·SHA-256을 바인딩한다. 카드 HVK와 로컬 CVC 키는 사용하지 않는다.
저장소는 저장소 코드 경로 밖의 서비스 소유 0700 디렉터리, 파일은 0600이며 모든 경로 구성요소의
심볼릭 링크와 파일 hard link를 거부한다. 파일을 독점 생성하며 원본 파일명은 물리 경로에 사용하지 않는다.
다운로드는 복호화·checksum 확인 후 현재 세션과 기기를 다시 검증한다. 잘못된 키/암호문은 503으로 실패한다.

실제 ClamAV 검사 뒤 별도 자원 제한 프로세스에서 이미지/PDF 구조와 카드 라벨/PAN OCR를 검사한다.
검사기 미설정·중지·오래된 서명·읽을 수 없는 문서를 허용 결과로 취급하지 않는다. OCR 결과는 보관하지 않는다.
OCR는 모든 카드 사진을 완벽하게 식별하지 못하므로 카드 typed target 금지·사용자 확인·보수적 파일 제한을
함께 적용한다. ClamAV 내부 임시 입력은 swap 금지 전용 RAM tmpfs로 한정하며 영속 디스크에 남기지 않는다.
실제 도구의 고정 버전·격리·제한은 [도구 검증 기록](../infra/documents/README.md)을 참고한다.
이 도구 시험 이미지와 운영 배포 구성은 구분하며 배포 시 같은 격리 조건을 적용하고 검증해야 한다.

## 6. 로그와 감사

기록할 수 있는 것: actor ID, 자원 ID, 작업 종류, 시각, request ID, 성공/실패, 버전.
일반 금액 정정 이력은 가계 접근 권한으로 보호한다.
기록하지 않는 것: 전체 PAN·CVC·유효기간 평문·계좌번호 원문·비밀번호·인증토큰·복구코드·진료서류 원문.
보관함 작업 감사에는 '열람 요청/실패' 같은 메타정보만 포함한다. 지문 결과를 서버가 직접 검증했다고 기록하지 않는다.
서버에서 볼 수 없는 로컬 화면 표시 성공은 클라이언트 보고라는 신뢰 수준을 구분한다.

## 7. 복구·분실

계정 복구와 보관함 복구를 분리한다. 계정 비밀번호 재설정으로 카드 암호화를 해제할 수 없어야 한다.
기기 분실 신고는 해당 세션과 등록 상태를 즉시 폐기한다.
이미 기기에 있었던 비밀의 원격 삭제는 오프라인 상태에서 보장할 수 없다.
공유 키를 가진 구성원 철회 시 새 키로 재암호화하고 예전 복사본 회수 불가능성을 고지한다.
상세 절차는 [키 수명주기](vault-key-lifecycle.md)에 따른다.

## 8. 출시 보안 게이트

G1: 정상/타가계 권한, 세션 만료·재사용·CSRF 확인.
G2: 보관함 암호화 벡터, nonce/AAD, 키 분리·회전·복구 확인.
G3: 실기기 지문 변경·잠금·취소·백그라운드·앱 강제종료·재설치 확인.
G4: 프록시·로그·DB·백업·bridge·WebView 상태에서 CVC/PAN 평문 유출 검사.
G5: 웹 XSS/의존 스크립트 경계와 첨부 접근, 네이티브 bridge 입력 검증.
G6: 운영 백업 복원·APK 서명·업데이트·분실 대응 실증.

보안 게이트가 실패한 기능을 숨긴 채 v1 완료로 처리하지 않는다.

### SB-017 카드 일반정보 경계

카드 일반 API는 마지막 네 자리만 입력·반환한다. 전체 PAN/유효기간/CVC/암호문을 전달하는 일반 요청은 strict extra-field 검증으로 거부한다. 카드 소유자와 가계 권한을 분리해 같은 가계의 두 계정이 모두 관리하며 다른 가계 ID는 API와 DB FK에서 차단한다. 이 단계는 카드 비밀 보관함을 제공하거나 전체 앱 E2EE를 주장하지 않는다.

SB-019 증권번호는 계좌번호와 같은 서버 필드 keyring을 사용하되 AES-GCM AAD의 필드 식별자를 `policy_number`로 분리한다. 가계·정책 ID·키 버전도 바인딩하며 암호문 치환은 실패한다. 일반 JSON에는 마스킹만 반환한다. 열람은 현재 Session/Device를 먼저 잠그고 가계·정책 잠금 대기 이후, 복호화 전후, 감사 flush 이후에 최근 인증과 현재 세션을 확인한다. 이 서버 암호화는 카드 보관함 E2EE와 별개이며 실제 운영 키는 개발 과정에서 저장소에 만들지 않는다.


SB-028~032 서버는 계정 세션→기기→가계→보관함 순서로 잠그고 반환/commit 직전에도 인증을 검사한다.
최근 인증 또는 목적·대상에 묶인 일회성 step-up은 관리 작업에만 사용하고 클라이언트 생체 bool을 받지 않는다.
별도 보관함 권한이 없는 가계 구성원과 철회된 구성원은 카드/wrapping 암호문을 읽을 수 없다.
서버는 암호문 내부의 실제 카드와 last4 일치를 증명할 수 없으며, 클라이언트가 GCM tag/고정 payload/
key check를 대조해야 한다. 포맷은 [확정 ADR](adr/vault-format-v1.md)을 따른다.
독립 코드 검토와 실제 DB 우회 시험은 [서버 검증](testing/vault-server.md)에 구분해서 기록한다.

### SB-037 사용자 파일 발급 경계

사용자 내보내기는 현재 가계의 업무 기록을 평문 JSON/CSV와 선택 문서 원본으로 내려주는 명시적 열람 동작이다. 보관함/인증 자료·전체 계좌/증권번호·서버 파일 경로는 명시적 공개 목록에서 제외한다. 최근 인증 또는 가계에 바인딩한 `data.export` 증명은 준비 전과 발급 직전에 검사하며 증명 소비·서버 발급 감사는 함께 커밋한다. ZIP 준비 중에는 인증 잠금을 유지하지 않아 로그아웃/기기 철회가 진행될 수 있고, 철회된 요청은 파일 첫 바이트 전송 전에 거부한다. 사용자 메모와 선택 원본 문서 안의 텍스트를 자동 비식별화했다고 주장하지 않는다. 다운로드된 로컬 파일은 원격 회수하거나 만료시킬 수 없다. 자세한 형식·한도·감사 투영은 [API 계약](api-contract.md#sb-037-사용자-내보내기감사-조회-구현-계약-r20)을 따른다.
