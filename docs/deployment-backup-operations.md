# 배포·백업·운영

## 1. 운영 형태

상시 실행 호스트 1대에 Docker Compose를 사용한다.
Caddy만 외부 HTTPS 포트를 노출하고 PostgreSQL/파일 저장소는 내부 네트워크에서 접근한다.
사용자 결정에 따라 현재 PC의 WSL에서 기존 서비스와 분리한 Compose 프로젝트로 운영한다.
기존 컨테이너·DB·포트·호스트 Tailscale 설정은 변경하지 않는다.
전용 Tailscale 노드의 Serve 8443은 앱/API, Funnel 443은 검증 정적 파일만 제공한다.
PC 절전/종료·WSL 중단 시 이용이 중단되므로 자동 복귀와 상태 점검을 운영 인수에 포함한다.
실제 노드 FQDN·비밀은 운영 단계에 주입하며 가상 값을 운영 주소로 표시하지 않는다.
[승인된 격리 운영 결정](adr/private-network-and-app-identity.md)을 따른다.

## 2. 설정 변수의 범주

PUBLIC_ORIGIN, API_ORIGIN, WEBAUTHN_RP_ID, ALLOWED_ORIGINS, DATABASE_URL,
DOCUMENT_STORAGE_PATH, SERVER_ENCRYPTION_KEY_FILE, COOKIE/SESSION 설정,
BACKUP_DESTINATION, APP_MIN_SUPPORTED_VERSION, LOG_LEVEL.
Android applicationId/서명 fingerprint는 빌드 설정 및 Digital Asset Links와 일치시킨다.
실제 값은 .env/secret store로 관리하고 .env.example에는 키 이름과 무해한 예시만 둔다.

## 3. 배포 흐름

합성 staging 검증 → 현재 DB/첨부 백업 → 스키마 확장 migration → 호환 API 배포 → 웹 갱신 → Android 정식 빌드/검증 → 두 기기 업데이트.
Android가 즉시 업데이트되지 않을 수 있으므로 새 API가 이전 지원 앱의 요청을 처리하도록 한다.
파괴적 스키마 변경은 구버전 앱 지원 종료 이후 별도 migration으로 수행한다.
롤백 계획은 앱/API 이미지 되돌리기와 DB 데이터 변환을 구분한다. DB downgrade가 언제나 안전하다고 가정하지 않는다.

## 4. APK 서명·배포

정식 APK는 별도 release 서명키를 사용하고 debug 기능을 끈다.
같은 앱 업데이트를 위한 applicationId·서명키·versionCode 관리 정책을 유지한다([S18, S19](references.md)).
서명키는 DB 암호화키·vault 복구코드와 다른 자산이며 Git/DB/일반 artifact에 포함하지 않는다.
서명키 암호화 백업과 분실 대응을 정하고 실제 업그레이드 설치를 두 기기에서 테스트한다.
앱 바이너리는 private release 또는 인증된 다운로드 경로로 제공한다. GitHub token을 APK에 내장하지 않는다.

직접 APK 설치도 OS·기기·개발자 검증 정책의 영향을 받는다.
출시 시 [Android 개발자 검증 공식 안내 S20](references.md)에서 배포 경로·지역·계정 요건을 다시 확인한다.
Play Store 공개가 v1의 선행조건은 아니지만, 직접 설치가 모든 기기에서 무조건 된다고 단정하지 않는다.
서버가 사용자 승인 없이 임의 APK를 설치하는 자동 업데이트는 구현하지 않는다.

## 5. 서버 백업

백업 대상: PostgreSQL, 비공개 첨부, 설정의 복구 가능한 암호화 사본, 스키마/앱 버전 메타데이터.
키와 데이터는 접근 통제를 분리한다. 백업 저장소 자격증명으로 모든 평문 복구키를 함께 얻을 수 있게 만들지 않는다.
CVC는 서버에 없으므로 서버 백업에도 없다. 카드 envelope/wrapping은 백업하되 복구코드 원문은 별도 보관이다.

설계 기본 보존: 일별 14개·주별 8개·월별 12개. 보존 기간은 저장공간과 민감성 검토 후 설정으로 확정한다.
백업 목표 RPO 24시간, RTO 4시간은 **설계 목표**이며 실측/보장 수치가 아니다.
백업 생성 성공과 실제 복구 성공을 각각 관측한다.
월 1회 격리 복원 시험을 권장 정책으로 두고 실행은 운영 스케줄 도구에서 구성한다.

## 6. 복원 연습

빈 서버 준비 → 같은/호환 PostgreSQL 설치 → DB 복구 → 첨부 복구 → 서버 암호화키 안전 주입 → migration 상태 확인 →
두 계정 로그인 → 자산 합계·보험 정산·재고·파일 checksum 대조 → 카드 보관함 복구 경로 확인.
실제 복구키는 기록하지 않고 복구 결과만 남긴다.
로컬 CVC와 기기 non-exportable key는 복원 대상이 아니다.

## 7. 내보내기

기본 내보내기는 자산/계좌/카드 일반정보/수입/고정비/보험/가전·재고의 JSON/CSV와 선택한 문서다.
PAN/CVC/보관함키/세션/로그인 해시는 기본 export에 포함하지 않는다.
운영 백업과 사용자가 내려받는 가계 export는 별도 기능이다.
내보내기에는 최근 재인증, 유효기간 제한, 감사기록, 파일 다운로드 후 로컬 보관 주의 안내를 둔다.
복원 가능한 운영 백업에는 카드 암호문이 들어가더라도 사용자 보고서에 암호문을 무의미하게 노출하지 않는다.

SB-037 사용자 API는 직접 ZIP을 응답하며 서버 파일/다운로드 URL을 보관하지 않는다. 준비/발급은 30초, 전송은 120초로 제한한다. 이미 내려받은 파일은 만료되지 않는다. 파일에는 진료 기록과 선택 문서 원본이 포함될 수 있으므로 화면을 연결할 때 저장 위치와 공유 범위를 사용자에게 안내해야 한다. 운영 백업 보존/키 분리/새 서버 복원 시험은 이 API와 별도로 검증한다. 상세한 필드 제외, CSV `text:` 규칙, 용량 한도와 감사 의미는 [API 계약의 SB-037 절](api-contract.md#sb-037-사용자-내보내기감사-조회-구현-계약-r20)에 따른다.

## 8. 관측·장애

health/readiness는 개인 데이터 없이 상태만 반환한다.
오류율·지연·DB용량·백업상태·예정 생성 마지막 실행을 기록한다. 요청 본문/진료명/카드번호는 수집하지 않는다.
예정 회차 생성 실패는 다음 실행에서 멱등하게 보충한다.
DB 장애 때 앱은 오래된 데이터를 성공 저장한 것처럼 표시하지 않는다.

분실 기기: 세션 폐기 → 기기 차단 → 필요 시 vault 회전 → 로컬 비밀과 카드 자체 위험 점검.
키 유출: 영향을 받은 키 종류 파악 → 신규 키/서명 정책 → 노출 사본 회수 불가능성 안내.
로그 유출: 원본보존 범위 확인 → 접근 차단·비밀폐기·원인 수정 → 더미 데이터로 회귀 테스트.
