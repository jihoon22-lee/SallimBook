# 실제 작업 시나리오 기반 UI/UX 개선

기준일: 2026-10-18. 관련 Issue [#100](https://github.com/jihoon22-lee/SallimBook/issues/100).
R-03~R-10, R-13~R-19, R-22의 화면과 작업 동선을 개선한다.
사용자가 직접 테스트하고 문제를 새 이슈로 등록한다는 결정은 유지한다. 실기기 인수나 백업 대기를 다시 만들지 않는다.

## 조사 방법

실제 사용자 자료 대신 저장소의 합성 가계 fixture를 사용했다. 자산·계좌·수입·고정 납부·카드·보험·가전·소모품·내보내기·설정의
25개 화면을 390×844 모바일과 1440×1000 PC 화면에서 각각 렌더링해 비교했다. 브라우저 캡처 50개는 화면 조사이며,
50개 업무를 완료했다는 뜻은 아니다. 별도의 클릭 시나리오에서 입력·저장·취소·오류 복귀와 기록 변경을 검사한다.

기존 설계와 계산 예제는 유지하고, 주 작업의 위치·선택 정보의 노출·입력 순서·초점 이동을 바꾼다.
모든 화면을 짧게 만드는 것을 목표로 삼지 않는다. 필드가 붙어 있던 보험금·납부 규칙 폼은 읽을 수 있는 간격을 확보하면서
높이가 늘 수 있으며, 소모품 화면은 전체 길이보다 재고 확인과 교체 작업에 도달하는 순서를 우선한다.

## 지연 응답 중 연속 작업 재현

반환 저장 응답을 500ms 늦춘 Android bridge 모의 시험에서, 반환 응답을 기다리는 동안 기존 수입의
무효 버튼을 누를 수 있었다. 실제 관찰된 요청은 새 반환 기록이 아닌 이전 수입 ID를 가리켰고 서버 fixture가 거부했다.
화면 레이아웃만 바꿔 숨기지 않고, 수입·납부 작업을 연 동안 다른 명령을 잠그고 요청 대기 중에는 입력 패널을 닫지 않도록 했다.
명시적인 요청 대기 중단과 결과 불확실 안내는 유지한다.

재현 테스트는 고정 시간만 기다리지 않고 응답을 보류하는 barrier를 사용한다. 응답 대기 중 다른 명령과 닫기가 비활성인지,
응답 후 새 반환 ID에만 무효 요청을 보내는지, 납부가 한 번만 기록되는지 검증한다.

## 결과 해석과 보존한 경계

- 합계는 서버 응답을 표시한다. 수입·납부·보험금 입력으로 스냅샷을 자동 가감하지 않는다.
- 월 기록의 당시 지분·범위, 미입력/0원/불러온 값 미확인 구분은 상세와 입력 흐름에서 유지한다.
- 금전 이벤트·재고의 멱등성 키, 버전 충돌 비교, 반환·무효의 구분을 바꾸지 않는다.
- 실제 비용을 여러 청구에 연결해도 원본 지출은 한 번만 합산한다. 보험금의 실제 수령과 반환을 구분한다.
- 카드 목록은 기존 마스킹 메타데이터만 사용한다. CVC 비활성 상태와 native 비밀 표시 경계를 유지한다.
- API 계약·DB 마이그레이션·금액 계산·암호화 정책 변경은 없다.

## 검증 기록

- `pnpm typecheck`, `pnpm build`: 성공. 기존 bundle 크기 경고는 임계값을 올리지 않고 남겼다.
- 25개 화면 × 모바일/PC 캡처: 50개 렌더링 성공. 변경된 월 확인·회차·보험 사건·납부 규칙은 후속 캡처도 수행했다.
- `pnpm exec playwright test --workers 6 --max-failures 20`: 첫 전체 실행 1,137 통과 / 11 실패.
  수입 연속 작업 경합 2건, 새 삭제 메뉴의 펼침 누락 2건, 단일 월 표시에 맞지 않는 기존 문구 검사 6건,
  26개 경로를 한 테스트에서 순차 검사하던 총 시간 제한 1건이었다.
- 경합 수정과 테스트 동선 보완 뒤 관련 7개 파일을 재검사했다: 208 통과 / 2 실패.
  남은 2건은 웹 fixture의 실제 응답 경로를 보류하지 못한 새 지연 검사 설정이었다. HTTP 응답을 직접 보류하도록 수정했다.
- `pnpm exec playwright test tests/task-journeys.spec.ts --workers 4`: **44 통과**.
  22개 시나리오를 PC와 Android 크기에서 각각 검사하며, 앞선 지연 검사와 사용자 지정 재고 단위 검사를 포함한다.
- 경로 검사는 26개를 개별 테스트로 나눠 직접 진입·새로고침·가짜 기록 부재·오류 부재·가로 넘침 검사를 모두 유지했다.
- 기존 필터·관리·이력 테스트에는 사용자가 누르는 펼침 동작을 추가했다. 금액·권한·서버 요청·충돌·전송 차단 검사를 제거하지 않았다.

- 첫 원격 전체 웹 UI 실행 `39112715111`은 **1,206 통과**했다. 뒤이은 실제 HTTPS 보험 시험은
  선택 영수증 정보와 사건 이력을 펼치지 않은 기존 테스트 때문에 실패했다. 의료기관 입력 전에 참고 정보를
  펼치고, 이력 검사 전에 변경 이력을 펼치도록 보완했다. 같은 이유로 기기 연결 삭제 시험도 관리 영역을 연다.
- 수정 후 `scripts/test_web_auth.py --insurance`, `--homecare`, `--months`, `--comparison`, `--cashflow`는
  각각 실제 API/PostgreSQL에서 통과했다. 금액·상태·이력 검증은 유지했다.

후속 배포에서는 백업·복원 점검 예약의 중단 상태와 독립 디스크 검사를 유지한다. 새 배포 소스에 대한 백업이
없으면 기존 health 작업의 `BACKUP_MISSING` 기록을 남긴다. 사용자 백업 유예 정책에서 서비스 성공으로 다룰 수
있는 것은 정확한 `BACKUP_MISSING` 또는 `BACKUP_STALE`뿐이며, 별도 상태는 `backup-deferred`,
`backup_verified=false`다. 서비스·검사 DB·디스크 오류와 미완료 복구는 실패로 유지한다. 이 운영 보조 정책은
제품의 백업 검증을 통과시킨 것으로 해석하지 않는다. 실제 활성화와 HTTPS 배포 확인 결과는 Issue #100에 남긴다.

원격 전체 CI와 실제 Android 계측의 결과는 Issue #100에 연결된 PR의 checks에서 확인한다.
브라우저 Android bridge 모의 시험과 실제 Android 계측·실기기 시험을 구분한다.
